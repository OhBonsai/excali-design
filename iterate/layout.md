# layout 待思考点(记录 · 非模型 reference)

> 布局 / 连线相关的开放思考。本轮先处理了「过度强调正交」,其余留作后续。

## 1. 不为正交而正交(本轮已落地一半)

**问题**:技能此前过度强调正交连线——`arch-lint` 有 `diagonal` 规则,把斜线段一律报 warn,
等于在逼「所有线走直角」。但:

- **正交 / 斜线 / 曲线都是好选择**,取决于图与可读性。正交读作「工程化」,斜线读作「直接」,
  曲线适合表达「关系」而非「流程」、让放射/有机图更自然。**为正交而正交 = 把跨层线压成平行束(条形码),反而更糟**(anti-slop 早就指出过)。
- **真正的连线问题**不是「斜」,而是:穿过无关框(arrow-thru)、绕到框背面把流向画反(wrong-attach-side)、
  交叉(crossings)、端口拥挤(port-*)。这些各有专门规则管,与「斜不斜」无关。

**已做**:删掉 `arch-lint` 的 `diagonal` 规则 + FIXES 项;同步更新 anti-slop / architecture-workflow / arch-lint.md / SKILL.md 的措辞(正交不再是「唯一正确」,是一种可选风格)。

**铁律(本轮要确立的核心)**:**路由绝不能反向影响 node 布局。**
- 布局(node 位置)先定;连线是**下游**,只在既定坐标间找路径。
- 绝不为了「让线走直角好看」去挪动、压缩、对齐 node ——那是路由污染布局,本末倒置。
- 顺序永远是 `layout(定 node)→ route(连线,风格自由)→ lint(查穿框/绕背/交叉,不查斜)`,**route 不回写 layout**。

## 2. 待思考(后续)

- **路由风格该不该由 data.ir / 图类型决定?** 比如:架构=正交或直连皆可;mindmap/放射=曲线;
  时序=直线。可否让 dispatch 顺带给一个「建议路由风格」,但仍只作建议、不强制。
- **曲线路由的避让**:`arch-connect` 目前只做正交两点连接 + 端口分布,不做避障(中间有框会压过去)。
  曲线/贝塞尔绕障是否值得做?还是继续靠「让相关 node 相邻」从布局上规避(更省)?
- **routing ≠ layout 的边界如何在代码上保证**:目前是约定(arch-connect 只读坐标、不改 node)。
  要不要加一个校验:对比 route 前后 node 的 x/y/w/h,**若 node 被路由步骤改动 → 报错**(机械守住「路由不污染布局」这条铁律)。
- **lint 只查「脏」不查「斜」**:确认 `arch-lint` 现在对斜线/曲线零惩罚;`floor-check` 的 squint 也不应因斜线扣分。
