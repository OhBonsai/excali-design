# 软件架构图工作流

> 画系统架构 / 服务拓扑 / 数据流 / 时序 / 部署 / 信息架构图。
> 核心:**先从代码/文档抽真实结构(原则 #0)→ 选抽象层级 → 单向数据流布局 → 语义配色**。

## 1. 抽取真实结构(原则 #0,最重要)

画**真实系统**前,先从「资产」抽结构,不臆测:
- `docker-compose.yml` / `k8s/*.yaml` → 服务清单 + 依赖 + 端口
- 模块/包目录(`src/` `services/` `packages/`)→ 组件边界
- `package.json` / `go.mod` / `pom.xml` → 技术栈、外部依赖
- `README` / 现有架构文档 / ADR → 设计意图
- 公开系统 → `WebSearch` 官方架构文档

抽出来写进 `system-facts.md`:服务列表、依赖边、数据流向、技术栈、外部系统。**图从这份事实长出来。**

## 2. 选抽象层级(C4 心智)

一张图只表达**一个层级**,别混:

| 层级 | 画什么 | 节点粒度 |
|---|---|---|
| **Context** | 系统 + 外部用户/系统 | 整个系统是一个框 |
| **Container** | 可部署单元(服务/DB/队列/前端) | 每个服务一个框(最常用) |
| **Component** | 单个服务内部模块 | 类/模块级 |
| **部署拓扑** | 物理/云资源(VPC/节点/region) | 基础设施 |

模糊时默认 **Container 级**——和工程对齐最有用。一次只画一层,要细就再出一张下钻图。

## 3. 布局:单向数据流(反面条图)

- **主数据流方向固定**:左→右(请求链路)或 上→下(分层)。全图一致。
- **分层背景**:用大的浅色 `area` 框圈出层(接入层/服务层/数据层),层内放节点。
- **减少箭头交叉**:同层节点对齐,跨层连线尽量平行;实在要交叉用路由点。
- **外部依赖**靠边放,用虚线连(`strokeStyle: dashed`)区分内部/外部。
- 网格对齐(20px),同层节点 y 对齐、等距。

## 4. 节点与图标

- 节点 = rectangle(服务)/ cylinder 形(DB,用 ellipse+line 或 excali-tech 库)/ diamond(决策/路由)
- 需要区分**类型**的节点配 `excali-tech` 库图标(库5);纯逻辑框不配(anti-slop)
- 每个节点:类型图标(可选)+ 名称 + 一行技术栈标注(如「Auth Service · Go」)
- actor/用户用 `excali-person`

## 5. 连线语义

- 箭头方向 = 数据/调用方向
- 线型编码:实线=同步调用,虚线=异步/事件,点线=可选/弱依赖
- 颜色编码:主链路 `#1971c2`、错误/降级路径 `#e03131`、其余 `#1e1e1e`
- 连线**必须 binding** 到节点(element-format.md),改布局不脱节
- 关键边可加 label(「gRPC」「Kafka topic: orders」),但别每条都标(噪音)

## 6. 配色(语义编码,见 color-system.md)

按**服务类别**分色,不是按好看:如「前端=蓝、后端=黑、数据=绿、外部=灰」。全图 ≤ 4 色。背景层用极浅色填充区分,不抢节点。

## 7. 时序图 / 流程图特例

- **时序图**:actor/服务横排顶部,各拉一条垂直 lifeline(line),消息用横向 arrow 按时间从上往下排,标消息名。
- **流程图/决策流**:用 `excali-shape`的 decision point / conditional branch;判定用 diamond,分支标 yes/no。
- **状态机**:状态用圆角 rectangle,转移用 arrow 标触发事件。

## 8. Junior pass → Full pass

**Junior**:只画分层背景 + 主节点框 + 主数据流箭头(骨架),show 给用户确认边界和层级对不对。
**Full**:补图标、技术栈标注、次要依赖、语义配色、对齐。

## 9. 验证(见 verification.md)

- 对照 `system-facts.md` 逐条核对:服务全 / 依赖方向对 / 没漏关键边
- 数据流方向一致、无误导
- 箭头 binding 正确
- 抽象层级单一(没混入下钻细节)
- 配色语义化、≤ 4 色
